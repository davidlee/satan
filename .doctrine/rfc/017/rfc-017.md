# RFC-017: SATAN extraction programme: sequencing and coordination

## Context

The extraction end-state is decided. **ADR-017** named the destination (Emacs is
a client; the trust boundary is a protocol property, not a process property).
**ADR-018** fixed the topology (one daemon repository, D1), the ownership of
policy + registry (D2), the transport (explicit RPC over a UDS; Postgres is a
state store not a bus, D3), the order (D4, policy-first / execution-last), and
the no-new-elisp-state rule (D5). **POL-001** supplies the per-module gate
("does it use the editor as an editor?") and, as amended 2026-07-22, the
retargeted seat lists and the D4 candidate ordering. **RFC-001** agreed the
direction in principle; **RFC-016** frames the evolution the daemons enable.

What no artifact holds is the **programme**: the accepted decisions describe a
destination and an order, but the effort that reaches them is a sequence of
slices spanning months, each carrying the same invariants, several with a hard
dependency on two obligations that are *not yet written*, and some able to run
in parallel while others are strictly serial. Driving that off ADR-018 D4 read
per-slice invites exactly the failure ADR-018 documents: the `satan-run.el`
clone (SL-013's subject) happened because a boundary was crossed without a
coordinating discipline in view. D4.1 — the run-context collapse — landed as
SL-013 (done, 2026-07-23). The next step (D4.2) is the first *authority* item,
and it is blocked.

This RFC asserts no new canon. It sequences and coordinates the execution of
canon already accepted, and surfaces the coordination questions that ADR-018
left open (chiefly OQ-1, the execution model). Where it appears to decide, it is
restating ADR-018/POL-001; where it genuinely opens a question, it says so.

## Discussion

### D1 — The programme spine

The extraction is one ordered programme of discrete slices, each a cutover, each
citing a destination in ADR-018 and a gate in POL-001. Restating ADR-018 D4 as a
coordinated roadmap with explicit ids and gates:

| Step | Work | Destination | Vehicle | State | Gate |
|---|---|---|---|---|---|
| D4.1 | Collapse run-context duplication (precondition, not an extraction) | in-language | SL-013 | **done** | — |
| G1 | Protocol tech spec (ADR-017 obligation) | `doctrine spec` | tech spec | **not written** | blocks D4.2 |
| G2 | Authority ledger scaffold (ADR-017 §3) | ADR-017 §3 / spec-cited | slice | **not written** | blocks D4.2 |
| D4.2 | Policy + tool registry → core, published read-only | daemon core (ADR-018 D1) | slice | blocked on G1+G2 | POL-001 first candidate; VT-1 |
| D4.3a | Patch runner → `satan-patcher` | daemon (Go, incidental) | IMP-006 | in flight (pivot-pending) | POL-001 trigger 1 |
| D4.3b | Memory substrate → `satan-memoryd` | daemon (Rust) | IMP-007 | deferred | POL-001 trigger; biggest editor-mismatch |
| D4.3c | Audit verifier → `satan-audit` CLI | CLI (Rust) | IMP-008 | deferred | POL-001 trigger; CI-useful |
| D4.3d | Observer → daemon | daemon | IMP-009 | deferred | folds into IMP-007 or stands alone |
| D4.4 | Run execution (spawn/filter/sentinel/finalize/budget) | daemon core | slice | last | gated on OQ-1 |

The ordering principle is ADR-018 D4's, verbatim: **policy-first,
execution-last**. Data-and-pure-functions before I/O; the largest, best-tested,
least-contested mass (run execution) moves last, when the execution model is
settled and the move is a quality win rather than a boundary fix.

### D2 — The two gates are the current critical path (G1, G2)

Nothing in the authority tier may migrate until both obligations ADR-017 records
as outstanding exist:

- **G1 — the protocol tech spec.** ADR-017's OQ resolved this is a *tech spec*
  (not an extension of `architecture.md`) precisely so it carries requirement
  ids: the authority ledger's rows cite them, and each migration's audit
  verifies the migrated invariant against something addressable. It writes down
  what today lives implicitly in broker code — schema-validated actions,
  mode/tool allowlists, append-only audit, ceilings, kill switches — as
  protocol invariants any surface must satisfy. Its shape interacts with
  ADR-018 OQ-2 (the RPC control-plane surface).
- **G2 — the authority ledger.** ADR-017 §3: every authority item (budget
  ceiling, allowlists, audit append, permission profiles, kill switches,
  arrival policy) names **exactly one owner at any time**, recorded as it
  migrates. Today the Emacs client owns them all; the ledger's first non-Emacs
  row is D4.2's policy/registry. Without the ledger, "no dual enforcement" is
  unverifiable and the split-authority hazard (ADR-017 negative consequence 3)
  is unmanaged.

G1 is the larger unit and gates G2's row schema (rows cite spec req ids). The
critical path is therefore **G1 → G2 → D4.2**. G1 is this RFC's immediate
successor (drafted alongside it).

### D3 — The ledger is the coordination instrument

The programme stays coherent across parallel and serial slices through one
device: the ADR-017 §3 ledger. One row per authority item; exactly one owner;
transitions recorded at the owning slice's **audit** (not its plan). A migration
that cannot show its ledger row moving from Emacs to core — with the old
enforcement deleted, not merely superseded — is not done. This is the
generalisation of ADR-018 VT-3 (retire the attrd bridge) and the ADR-017
"no dual enforcement" verification (grep both sides) to every authority item.

### D4 — Invariants every slice inherits

Independent of which item, every extraction slice carries the same contract, so
the design work is done once here and cited, not re-argued per slice:

1. **Cutover, never addition** (ADR-018 negative consequence; POL-001
   half-extraction hazard). The migrated invariant is enforced at exactly one
   point on landing. A duplicated policy table would be materially worse than
   the duplicated struct SL-013 removed.
2. **Disable switch on every extraction** (POL-001 standing principle; cf.
   `satan-patch-runner-enabled`).
3. **Fail closed with the client absent** (ADR-017 §4). Daemons under test with
   no Emacs process enforce their ceilings; they never fall open.
4. **Preserve the test corpus across the port** — ert becomes acceptance
   fixtures (POL-001). The broker suite is the strongest asset disturbed by
   D4.4; it is re-earned in Rust, not discarded.
5. **No new stateful layer lands in elisp** (ADR-018 D5) — hypothesis, probe,
   pattern are daemon-owned from day one.

### D5 — Parallelism and dependencies

Not everything is serial, and treating it as such wastes the substrate-tier
slack POL-001 already grants:

- **Strictly serial:** G1 → G2 → D4.2 (authority tier); D4.4 last of all.
- **Parallel-eligible:** the substrate handlers (D4.3a–d) are gated by POL-001
  *triggers*, not by the authority tier. IMP-006 (patch runner) is already in
  flight and file-disjoint from the policy/registry work; it need not wait on
  G1/G2. IMP-008 (audit verifier CLI) is mechanical and CI-useful and can be
  pulled forward whenever its trigger fires. IMP-007/IMP-009 may fold together
  (POL-001's IMP-009 note).
- **Sequencing hazard:** running D4.2 and a substrate handler that *reads the
  policy artifact* concurrently risks the reader pinning a pre-cutover shape.
  Coordinate through the published artifact's version stamp, not wall-clock.

This is the natural `/dispatch` shape later: file-disjoint slices parallelised,
conflicts reported not merged.

### D6 — Open coordination questions

Carried from ADR-018 / RFC-001, unresolved and owned by this programme:

- **OQ-1 (ADR-018) — execution model.** One executable or several; one process
  or several. Gates D4.4 and shapes the `satan-core` crate/workspace layout.
  Deliberately not decided here.
- **OQ-2 (ADR-018) — the RPC surface** is a new security boundary (D3). Its
  design interacts with G1's protocol spec; the spec should not front-run it but
  must leave room for it.
- **Where the emacs client package lives** (RFC-001 open) — the `satan` flake
  repo or its own. Affects how the read-only policy artifact is published and
  consumed.
- **Migration renumbering vs freeze-and-diverge** (RFC-001 D4) — surfaces when
  IMP-007 moves the memory substrate and its migration runner.

## Outcome

Open. The spine (D1), the critical path (D2), the ledger-as-instrument (D3), and
the inherited invariants (D4) are proposed as the coordination frame; they
restate accepted canon and add no new law. The live questions are D6's —
chiefly OQ-1, which gates the tail of the programme (D4.4) and the crate layout.
The immediate, uncontested next action the RFC identifies is **G1: author the
protocol tech spec**, which unblocks everything in the authority tier.
