## Overview

SATAN is a personal AI agent system: scheduled and interactive model runs that
perceive the user's desktop and notes, reason in a sandbox, and act only through
a validated tool protocol. It spans several repos and processes. This is the
whole-system **context** spec (C4 level 1): it names the containers, how they
couple and how they are composed and confined, and holds the invariants that
hold across all of them. Each container's mechanism belongs to that container's
spec; this root never restates it.

Host-specific facts — paths, uids, host name, flake pins, systemd units, the
path table for every jail — are deployment, not architecture. They live in the
deployment note `~/flakes/SATAN.md`.

### Containers

| Container | Repo | Runtime | Owns | Spec |
|---|---|---|---|---|
| **Broker** | `satan` (elisp) | inside the Emacs daemon | mode/tool/capability policy, tool registry, run lifecycle, audit, MCP server, elisp migrations | — |
| **Harness** | `satan` (`satan/harness/`, Python) | subprocess per run, jailed | nothing durable; talks to models through the host LLM gateway | SPEC-003 |
| **Trust-boundary protocol** | cross-cutting | — | invariants every enacting surface satisfies | SPEC-001 |
| **Attribute daemon** (`satan-attrd`) | `satan-attrd` (Rust) | user service | attribute projection, events, decay; `notify-stream` bridge | — |
| **Interactive daemon** (`malebolge`) | `malebolge` (TypeScript) | on-demand user service; jailed launcher `jailed-malebolge`, room profile: no network | its durable conversations (`durable/room/`); model loop, persona and SATAN MCP on the host; coding tools in an oubliette room as its own room user | — |
| **Patch runner** (`satan-runner`) | `malebolge` (TypeScript, second binary beside the interactive daemon) | user service | patch jobs end to end: queue, job state and audit in its own SQLite store, durable agent conversations whose tools run in an oubliette room, collection into quarantine, per-job ceilings | SPEC-004 |
| **Perception** (panopticon) | `panopticon` (Python + Firefox extension) | user services + timers | behaviour logs (raw, segments, content, snapshots) | — |
| **goad** | `goad` (Rust/Slint) | graphical-session service | ask UI; its backend lives in the corpus | — |
| **Confinement** | jail library (bwrap); `oubliette` (microVM rooms; the patch runner's and the interactive daemon's tools run in room `assistant`) | per process / per room | sandbox profiles, rooms, quarantines | — |
| **Shared database** | Postgres `satan_memory` | system service | traces, interventions, attributes | — |
| **Text roots** | notes (user's), corpus (SATAN's, own repo), state (runtime) | files | see NF-005 | — |

The editor config and the host flake are **clients of** the system, not
containers: the editor config loads the broker; the host flake composes every
repo into one deployment, including the host LLM gateway that every model call
goes through.

### Current topology

```text
                  ┌──────── jails · UNTRUSTED ─────────┐
                  │  Harness       Interactive agents  │
                  └─────────▲─────────────────┬────────┘
                JSONL stdio │                 │ MCP (UDS)
                            │                 │
timers ──emacsclient──►┌────┴─────────────────▼────┐ SQL   ┌──────────────┐
                       │ Broker (Emacs daemon)     ├──────►│ satan_memory │
                       │                           │◄──┐   └──────▲───────┘
                       └──▲──────────┬──────────┬──┘   │          │inbox
                   files ro          │ r/w      │      │RPC   ┌───┴────┐
                   ┌──────┴───┐ ┌────▼─────┐ ┌──▼───┐  │(UDS) │ attrd  │
                   │perception│ │text roots│ │ goad │  │      └────────┘
                   └──────────┘ └──────────┘ └──────┘  │
                                                ┌──────┴───────┐   ┌───────────┐
                                                │ patch runner ├──►│ oubliette │
                                                └──────────────┘   │ room      │
                                                                   └───────────┘
                   ──────── file-coupled ────────────── ─ postgres-coupled ─
```

Broker → goad carries the queue file and `goad-emit`; attrd couples through
inbox tables with `pg_notify`. The patch runner couples to the broker only
over its own control socket (UDS RPC; ADR-018 D3) and keeps its state in its
own store; its agent's tools run in an oubliette room. The interactive agents
are jailed pi and the malebolge daemon. The daemon reaches the broker over MCP,
as pi does, runs its coding tools in the oubliette room over pi-env, and
reaches models only through the gateway's client socket.

### Transports

| Transport | Between | Plane | Note |
|---|---|---|---|
| Process + JSONL stdio | broker ⇄ harness | control | protocol: `docs/protocol.md` |
| HTTP, OpenAI-compatible | harness → LLM gateway, jailed pi → LLM gateway | data | per-client gateway key, passed by fd from the jail launcher; the gateway is host deployment, not a SATAN container (`~/flakes/SATAN.md`) |
| MCP (JSON-RPC over UDS) | interactive agent → broker | control | one connection per conversation window, plus one shared tool-list connection; the client names its conversation and kind in `initialize` (DEC-121, DEC-125); a run per connection, minted on the first `tools/call`, finalised on close (DEC-122) |
| `emacsclient --eval` | scheduler → broker | control | unauthenticated beyond socket permissions |
| Postgres tables + `pg_notify` | broker ⇄ attrd | control, carried by the data store | retired by ADR-018 D3 |
| NDJSON over UDS (control socket) | broker ⇄ patch runner | control | same-uid, never jailed; Emacs submits, watches and reports dispositions (SPEC-004) |
| ssh over the room's door relay; `capsule push`/`collect` | patch runner → oubliette room | control (tools), data (git) | work returns only as git into a host quarantine (SPEC-004) |
| pi-env over ssh through the room's door socket | interactive daemon → oubliette room | control (tools) | as its own room user; `/work` clones are read-only to it, and its work reaches the host only as a patch job |
| HTTP over the gateway's client socket (UDS) | interactive daemon → LLM gateway | data | the daemon's jail has no network; its gateway key is a read-only file |
| Files (append-only logs, snapshots, queue file) | perception → broker, broker ⇄ goad, broker ⇄ text roots | data | |

### End-state (forward intent)

ADR-018: one core daemon repo owns policy + registry (published read-only),
run lifecycle, attributes and all migrations; Emacs becomes a client holding
the human approval surfaces; the control plane is UDS RPC; Postgres is a state
store only. Undecided: core process split (ADR-018 OQ-1) and where MCP is
served. Decided and built by SL-023: the patch runner lives in `malebolge`
(workload fit, ADR-018 D1 as amended), keeps its own store and runs its tools
in an oubliette room. Decided and built by SL-027: the interactive daemon is a
room client — coding tools in the room, model calls through the gateway
socket, its profile a launcher (ADR-017 ledger row 3b). The rest is not built; the topology above is the
verified current state.

## Responsibilities

Mirrors the structured list: name the containers and their coupling; classify
transports by plane; hold the system-wide invariants NF-001 to NF-006 (REQ-013 to
REQ-018); keep current topology and forward intent side by side and
distinguishable. The bar is **altitude** — composition, never mechanism.

## Concerns

- **Trust boundary reach.** SPEC-001 defines the protocol; this spec owns the
  question of which channels exist *around* it. A jail's mount list is part
  of the boundary (NF-004).
- **Two buses.** Containers couple either through Postgres or through files.
  The Postgres side carries control-plane traffic today, which is why its
  coupling is tighter than it looks (ADR-018 D3).
- **Shared database, split ownership.** Every Postgres-coupled container
  writes one database; schema authority must not be split (NF-001).
- **Composition and deployment.** The system is assembled from several repos
  by a host flake. Cycles and mixed revisions are system faults, not repo
  faults (NF-002, NF-003).
- **Single host process.** Until ADR-018 lands, the Emacs daemon is the
  broker's only host: its restart is a system restart, and loading the package
  starts subprocesses.

## Hypotheses

- **The container set is the right decomposition.** The patch runner and
  attribute daemon are containers today; ADR-018 D1 predicts attrd collapses
  into the core. The patch runner, now running its tools in an oubliette room,
  stays a separate container with its own spec (SPEC-004).
- **Files are the right data plane.** Perception and goad couple through
  durable files and never need request/response; if either grows a
  request/response need, it belongs on the control plane, not in a file.

## Decisions

- **D1 — Anchor-free synthesis.** No parent, no descent, no `[[source]]`: this
  context spec governs composition, not a code surface. Containers parent to
  it (SPEC-001 first).
- **D2 — Deployment facts live with the deployment.** Paths, uids, host
  names, pins, units and jail path tables are in `~/flakes/SATAN.md`. They
  change with the machine; this spec changes with decisions (NF-006 applies
  the same rule to code).
- **D3 — Gaps are backlog, not prose.** Observed violations of these
  invariants are filed as backlog items and cited from the requirement
  rationale, so this spec stays evergreen.
- **D4 — Diagrams are generated.** `diagrams.py` in this folder writes the
  three HTML diagrams (`python3 diagrams.py .`); the text diagram above is
  maintained by hand.
