# RFC-018: Durable SATAN and brokered authority: auth-gateway, git-broker

## Context

Two working briefs (uncommitted, `docs/brief.{broker,durable}.local.md`)
propose SATAN's next shape. This RFC carries their substance into governance
and lines it up against accepted canon. It asserts no canon itself.

**Brokered authority.** The broker brief proposes a host-side process that
"lets an untrusted process ask a trusted process to exercise explicitly granted
authority on its behalf". It holds secrets, mediates selected capabilities and
audits them. A confined agent keeps familiar interfaces (a `git` binary, a
model endpoint), but behind them are thin shims that forward to the trusted
side. Its v0.1 goal: an ordinary jailed coding-agent session (Pi, in existing
confinement, on a disposable repo) can inspect, edit, `git diff/add/commit`,
call its model and request an authorised push. In the same session,
`git stash`, `git reset --hard`, `git clean`, arbitrary push, credential
inspection and unrestricted network are unavailable by construction. It is
meant to be useful without SATAN. Its non-goals include SATAN semantics, a
policy DSL and confinement machinery. This RFC splits it into two packages
(D1).

**Durable SATAN.** One persistent organism instead of a series of
reconstructed runs:

- **Pi Durable** as the harness: durable conversation, restart-safe turns,
  resume.
- **A semi-persistent microVM** as SATAN's *habitat*: writable project
  checkouts, read-only evidence mounts (panopticon etc.), writable private
  state.
- **Brokered authority** as the only route to authority outside the VM.

Its posture is "high autonomy inside the habitat; very little authority
outside it". Modes (`morning`, `tick`, `@satan`, self-edit, patch) become
*event classes* delivered to that one organism.

Forces:

- **Live defects that brokered authority removes structurally.** ISS-029:
  provider keys are forwarded with `try-fwd-env`, which puts them on bwrap's
  argv. ISS-028: dev jails bind the editor's eval socket. Both violate SPEC-002
  NF-004 (REQ-016). Today the credential path is
  `satan-broker-provider-key-vars` (`satan/satan-broker.el`) plus
  `satan-patch-adapter-pi-api-key-vars`. Keys enter the jail as environment.
- **Ownership of the capability concept is already assigned.** ADR-017/018
  give policy (allowlists, capabilities, profiles, budgets) to one owner,
  `emacs-client` today and `daemon-core` after D4.2, and publish it read-only
  for every surface to read (ADR-018 D2, SPEC-001 REQ-006). A new generic
  "principal × capability" authority would compete for that ownership.
- **Durable SATAN reopens accepted sequencing.** ADR-018 D4 and RFC-017 D1
  move run execution *last* (D4.4), gated on ADR-018 OQ-1, the execution
  model. A persistent organism under Pi Durable is a candidate answer to OQ-1,
  and it relocates run execution out of SATAN's own code entirely.

## Discussion

### D1: Two focused enforcement packages; policy stays where it is

```text
policy owner          what is permitted: modes, tools, capabilities, profiles,
(emacs-client →       budget ceilings.  Published read-only (ADR-018 D2).
 daemon-core)         Unchanged by this RFC.
        │ grants, per session
        ▼
auth-gateway          owns LLM authority: provider-credential custody,
                      model/provider restriction, per-session token cap.
git-broker            owns Git authority: real git behind a shim, argv
                      allowlist, remote credentials, permitted refs.
        │ both serve confined clients over a Unix socket
        ▼
confinement           bwrap jail profiles · oubliette capsules (microVM).
                      what a process can reach at all.
```

- **Two packages, not one broker.** Each mediates one substrate and holds one
  kind of secret. There is reusable Pi-specific prior art for each, and they
  have no shared logic worth a common core. One generic broker would have to
  invent the "principal × capability × resource" model the broker brief
  describes, and that model already has an owner.
- **The packages enforce; they do not define.** What a session may do is
  policy, owned per ADR-018 D2. Each package enforces a grant it is handed and
  holds the secrets needed to act on it. In ledger terms, the packages own
  *custody* and *enforcement* items. Allowlist and profile rows (2, 3) keep
  their owner.
- **Confinement vs packages.** Confinement decides *reach*; the packages
  decide *authority beyond reach*. They compose, and neither replaces the
  other.
- **Home.** Each package lives outside this repo and depends on nothing in
  `satan`. Doctrine dispatch workers and oubliette capsules consume them too,
  and SPEC-002 NF-002 requires acyclic composition. The host flake runs the
  daemons. This repo consumes only the client side (shim, base URL, socket
  bind).

### D2: The git allowlist serves two purposes, in every profile

Agents handle complex git competently but reliably destroy a session's work
with a small set of common commands (`stash`, `reset --hard`, `clean`,
`checkout`/`switch` over a dirty tree, …). That holds whether the checkout is
the user's host tree or the agent's own clone in a microVM.

| Purpose | Covers | Applies |
|---|---|---|
| **Work protection** | local ops: allowlist of subcommand + argument shape | every profile, host tree or habitat |
| **Authority** | remote ops: push to permitted refs, with git-broker-held credentials | every profile |

Both purposes belong to `git-broker` and share one mechanism (the shim plus the
allowlist), but they are separate ledger rows (D3). Work protection is a
guardrail on the agent's own environment; authority is exercise beyond it.

Consequence for the microVM: if host-side git executes local ops, the host must
see the VM's working tree (a virtiofs share or similar). The alternative is a
host-side policy check with execution inside the VM, which moves enforcement
inside the habitat SATAN controls. See OQ-3.

### D3: Proposed authority-ledger changes

New owner tokens: `auth-gateway`, `git-broker`.

Proposed new rows. None is transitioned yet; each enters as owned by its
current holder, and the move is recorded at the migrating slice's audit
(ledger INV-3).

| # | Authority item | Owner today | Proposed owner | Enforced at today |
|---|---|---|---|---|
| 8 | Provider credential custody | `emacs-client` | `auth-gateway` | `satan-broker-provider-key-vars` → jail env (satan-broker.el); `satan-patch-adapter-pi-api-key-vars` |
| 9 | Remote git authority (push, credentials, permitted refs) | unverified: no push site in `satan/`; satan-patcher's path not yet checked | `git-broker` | — |
| 10 | Agent local-git work protection (D2) | none: unenforced gap | `git-broker` | — |

Changes to existing rows:

- **Row 5 (token/budget ceiling)** conflates two duties. The *policy*, choosing
  a run's ceiling from mode and attributes, stays with the policy owner. The
  *enforcement backstop* is a hard per-session cap on model calls. That cap
  sits where the tokens actually flow, and it is the only place a cap survives
  a compromised harness. ISS-029 shows the current backstop silently disabled
  in the jail. Proposal: split row 5 into 5a (policy, unchanged owner) and 5b
  (enforcement, `auth-gateway`). The session grant carries the number. See
  OQ-2.
- **Row 4 (append-only audit).** Each package logs its own requests:
  principal, operation, policy result, execution result, and no secrets. Each
  log has exactly one writer, and none appends to SATAN's run audit, so row 4's
  existing dual-write hazard gains no third writer. Proposal: treat these logs
  as part of rows 8–10, recorded in each row's `Enforced at`, not as a
  separate audit row.

Ledger INV-2 requires every row to cite a SPEC-001 requirement or a governing
ADR. SPEC-001 has no requirement for secret custody. NF-004 (REQ-016) has
"secrets never appear on a process argv" only as an acceptance criterion. Rows
8–10 therefore need either new SPEC-001 requirements or the ADR in D6 to stand
in.

### D4: Durable SATAN against ADR-018

| Durable-brief element | Accepted canon it touches | Relationship |
|---|---|---|
| One persistent organism; modes become events | ADR-018 OQ-1 (execution model) | candidate answer: the core supervises one long-lived run |
| Pi Durable owns execution continuity | ADR-018 D4.4 (run execution last); RFC-017 D1 spine | relocates run execution to an external harness instead of porting ~980 lines of `satan-broker.el` |
| Pi Durable stays replaceable; SATAN semantics stay outside it | ADR-018 D2 (policy owned by core, read by surfaces) | consistent |
| Habitat = microVM | SPEC-002 Confinement (oubliette "not yet used"); ADR-018 open question on oubliette for the patch runner | promotes oubliette to SATAN's primary confinement |
| Self-edit → reviewable branch via `git-broker` push | IMP-006 / ISS-030 (patcher has never completed a job) | may subsume the patch runner's role |
| Private state (memory, hypotheses, patterns) inside the VM | ADR-018 D5 (no new elisp state; daemon-owned); Postgres as state store | **tension**: VM-local vs host Postgres. Unresolved (OQ-4) |

Neither package depends on any of this. Both are useful to today's bwrap
jails, which is why they can be sequenced first (D5).

### D5: Sequencing

| # | Step | Depends on | Pays down |
|---|---|---|---|
| 0 | This RFC; the two packages selected (adopt or build) | — | drift against ADR-017/018 |
| 1 | `auth-gateway`: harness and Pi point their base URL at it; keys leave the jail env | step 0 | ISS-029; rows 8, 5b |
| 2 | `git-broker` shim (D2 allowlist) in bwrap dev jails; drop `apiKeyJailOptions` | step 0 | rows 9, 10 |
| 3 | Both packages in oubliette capsules, replacing injected credentials | steps 1–2 | the packages' second, non-SATAN consumer |
| 4 | Durable SATAN habitat: capsule + Pi Durable + both packages | ADR-018 OQ-1 settled | durable-brief slices 1–2 |

Steps 1 and 2 are independent of each other and of RFC-017's authority-tier
critical path (G1 → G2 → D4.2). Step 4 is not.

ISS-028's eval-socket bind is jail-profile work, and neither step closes it.

### D6: Governance needed to make the direction stick

1. **ADR (next free id):** establish `auth-gateway` and `git-broker` as
   containers outside SATAN, with enforcement-and-custody ownership only; adopt
   the D2 two-purpose rule; add the legend tokens and rows 8–10; split row 5.
   It stands in for INV-2 until SPEC-001 grows matching requirements.
2. **SPEC-002 revision:** add both containers, their transports (UDS, control
   plane) and the new arrows; drop provider keys from the jail-env story.
3. **SPEC-001 requirement(s)** for secret custody (no credential ever enters a
   confined surface), unless the ADR is judged sufficient.
4. **ADR-018 amendment or successor**, only once OQ-1 is settled for the
   durable design. It is not needed for steps 1–3.

## Spike findings: Pi Durable as the harness (CHR-012, 2026-10-16)

Evidence for D4, not a decision. CHR-012 built `~/dev/pandaemonium`, a
host program that runs interactive SATAN on `@earendil-works/pi-durable` 1.3.0,
and verified it live against satan-mcp and `deepseek/deepseek-flash`.

```text
pandaemonium (daemon; sole owner of the session storage)
 ├─ pi-durable Harness on SQLite   $XDG_STATE_HOME/satan/durable/
 ├─ persona section                satan-corpus scaffold + prompts/interactive.txt
 ├─ CodingTools                    read · write · edit · bash
 ├─ satan extension                pi-mcp client ── UDS ──▶ satan-mcp (Emacs)
 └─ UDS $XDG_RUNTIME_DIR/satan/durable.sock  ◀── NDJSON ── clients
                                     terminal attach · Emacs comint
```

- **F1: Pi Durable is a library, not a harness binary.** It has no CLI and no
  TUI, and it does not load coding-agent extensions (`ExtensionAPI`). Its own
  `defineExtension`/`defineTool` model replaces them. "Pi Durable as the
  harness" therefore means a small host program of our own. It came to about
  680 lines of TypeScript, including the socket protocol and a client. The MCP
  bridge (`~/notes/.pi/extensions/satan.ts`, 363 lines) ports to 41 lines on
  pi-mcp plus a 92-line unix-socket transport. SATAN semantics stay outside pi-durable, which keeps
  D4's "stays replaceable" row intact.
- **F2: Crash recovery holds, and its tool semantics suit SATAN.** Test: the
  daemon was killed with SIGKILL during a 10-second `bash` call.
  - On restart the run resumed without resubmission. The call came back as an
    `interrupted` error result carrying the output committed before the kill
    (the model correctly reported "4").
  - Tools default to `replay: "unsafe"`, so a side-effecting SATAN tool is
    never silently re-run. Read-only tools could opt into `replay: "safe"`.
- **F3: One owner, many clients: the ADR-017 shape.** One process owns the
  storage. Clients attach through `watchEvents`, a JSON event stream that
  opens with a snapshot of the conversation. A late joiner gets the transcript
  and any answer in flight. The Emacs client is `comint` over the line client
  (about 40 lines of elisp): Emacs attaches and does not own the lifecycle.
  - **New surface:** the daemon socket grants submit and abort to any process
    able to connect. Today the guard is only the 0700 permissions on
    `$XDG_RUNTIME_DIR`. That needs a SPEC-001 view before any non-interactive
    use.
- **F4: Bearing on ADR-018 OQ-1 (execution model).** The spike shows "one
  long-lived run supervised outside Emacs" for the interactive mode only.
  pi-durable also accepts *passive entry writes* of custom kinds, queued
  through the conversation inbox. That is a plausible carrier for
  modes-as-event-classes (`tick`, `morning`, `@satan`). Untested.
- **F5: Bearing on OQ-3/OQ-4 (habitat).** `@earendil-works/pi-env` is a
  remote `ExecutionEnv`: a small daemon reached over SSH. With it the harness
  and its storage can stay host-side while tools execute in the microVM. The
  transcript would live on the host and the working tree in the VM. Untested.
- **F6: Credentials (D5 step 1) unchanged.** pandaemonium reads provider keys
  from its environment via `op run`, as jpi does, and runs unjailed. pi-ai
  providers take a base URL, so the LiteLLM gateway (`~/flakes` IDE-003) is a
  configuration change, not a code change.
- **F7: Small frictions.**
  - pi-ai's built-in model catalog lags the coding agent's remote catalog;
    pandaemonium reads `~/.pi/agent/models-store.json` to close the gap.
  - The persona section is re-read on every request. Corpus self-edits
    therefore land on the next turn, and the prompt cache survives because the
    harness resends only changed sections.
  - The interactive persona still carries the batch protocol plus a precedence
    override (IMP-032).

## Outcome

Open. The proposals: the D1 split into two enforcement packages with policy
ownership unchanged, the D2 two-purpose rule, the D3 ledger rows and the row 5
split, and the D5 order (packages first, durable SATAN after OQ-1). Open
questions:

- **OQ-1: adopt or build, per package.** Pi-specific prior art exists for
  both. Can it meet the broker brief's release security properties (no
  credential reachable from the jail, no unsupported git command, no arbitrary
  shell or network through the package, an inspectable log)? An adopted tool
  still takes its ledger slot.
- **OQ-2: budget enforcement.** Split row 5 as proposed, or keep the
  backstop SATAN-side? If split, the session grant must carry the ceiling, and
  the policy owner must not also enforce it (NF-001, REQ-009).
- **OQ-3: where local git executes for a microVM habitat.** Host git over a
  shared tree, or in-VM git with a host-side check? The second puts
  enforcement inside the habitat.
- **OQ-4: where durable SATAN's private state lives.** VM-local (habitat,
  discardable), host Postgres via the core, or split by kind. This interacts
  with ADR-018 D5 and the "habitat is not precious" principle.
- **OQ-5: how a grant reaches a package.** Each package has its own
  configuration (permitted models, refs, git argv shapes). For SATAN sessions,
  that configuration must be derived from the published policy artifact, not
  restated by hand (REQ-006). Who mints a session, and in what form: the
  host-side launcher (jail wrapper, capsule lifecycle), the policy owner, or
  both under one rule? Working premise: package config is JSON (ASM-003).
  Evaluation gate: an option qualifies only if its config can be generated
  from the policy artifact (CON-002).
