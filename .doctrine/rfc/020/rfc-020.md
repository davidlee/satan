# RFC-020: Belphegor: read-only mail for SATAN through a JMAP mirror outside the agent

## Context

A working brief (uncommitted, `docs/email-brief.local.md`) proposes letting
SATAN inspect, triage and summarise the user's Fastmail mail without gaining
authority to change the mailbox. It was written without access to this
system. This RFC restates it against local canon and the operator's direction
(2026-10-26), and asserts no canon itself.

The brief's principle stands: **inference, authority and execution are
separate.** In its words: the model proposes, deterministic software
validates, the human authorises, and privileged software executes.

Its shape, briefly:

- A standalone TypeScript adapter (library and JSON CLI) over JMAP, Fastmail's
  native JSON mail protocol (RFC 8620 core, RFC 8621 mail), authenticated with
  a read-only API token.
- Five read operations: `mailboxes`, `list`, `read` (bounded plain text),
  `thread` and `changes` (incremental, via JMAP state tokens).
- A normalised message model that keeps JMAP ids separate from RFC 5322
  `Message-ID`s.
- Hard size and count limits enforced in the adapter, not in prompts.
- All mail content treated as untrusted data.
- SATAN classifies mail (`action_required`, `awaiting`, `fyi`, `noise`) into
  an Org digest.
- A future executor applies human-approved operation plans (archive, move,
  `mark_read`, flag, unsubscribe, rules) with a separate write credential.
- Non-goals: sending or drafting mail, mutation in the first milestone,
  attachments, Gnus integration, a background daemon, and full-text
  indexing.

The brief left one architectural question open: can the agent harness call a
read-only broker without also reaching its credential? The answer decides
whether a CLI is enough or a service with IPC is needed.

Forces from this system that the brief could not see:

- **The host has a credential pattern.** `satan-runner` receives its gateway
  key by systemd `LoadCredential=` into `$CREDENTIALS_DIRECTORY`. No jail binds
  the credentials directory, and `just check-jails` asserts that
  (`~/flakes/SATAN.md` § Secrets).
- **Interactive SATAN has host coding tools.** malebolge's interactive daemon
  runs in a bwrap jail on the host, with network access, and its coding tools
  (bash included) also run on the host (`~/dev/malebolge/README.md` §
  "Where tools run"; RFC-019 Context). A token file the user can read is one
  `cat` away from that session unless the jail hides it.
- **ISS-028** (open): jails that hold model output can reach around the
  protocol. Dev jails bind the Emacs eval socket, and the harness probably has
  `~` mounted read-write. It violates SPEC-002 NF-004 (REQ-016).
- **Emacs is a client** (ADR-017). It keeps the human approval surfaces
  permanently, and lifecycle authority lives outside it. The operator's
  direction is that mail touches Emacs only as a review UI: no credentials and
  no process management.
- **Tools that do not need Emacs become pi-durable native tools** (RFC-019
  D6). pi-durable is the harness library under malebolge. Such tools run in
  the agent process on the host and must confine themselves to a root.
- **POL-001** makes Rust the target for SATAN-orbit daemons. TypeScript stands
  where the workload fits it (malebolge, the patch runner).
- **Three roots.** `~/notes` is read-only to SATAN. `~/satan-corpus` holds
  SATAN-authored model-facing text, and `~/.local/state/satan` holds
  discardable runtime state.

## Discussion

### D0: Names

Names chosen by the operator (2026-10-26):

| Name | What | Role |
|---|---|---|
| **Belphegor** | the mail subsystem as a whole | the demon of sloth and ingenious inventions; you never read your own correspondence |
| **Screwtape** | the Gleam JMAP connector: mirror unit, store, CLI; sole holder of the read credential | the infernal correspondence clerk, who fetches and presents mail |
| **Wormwood** | the future deterministic executor (D6) | the junior demon who carries out instructions under supervision |

Belphegor is an umbrella name, not a process. SATAN's triage run (D5) and the
Emacs review surface are Belphegor parts that Screwtape knows nothing about.

### D1: A scheduled mirror, not a callable broker

The operator chose a **scheduled mirror** over an on-demand CLI. A systemd
user timer starts a oneshot service. The service syncs JMAP into a local
store, and every consumer reads only that store.

```text
 Fastmail ──JMAP (read-only token)──▶ screwtape.service     (oneshot, timer; no LLM, no Emacs)
                                          │ token: encrypted credential (D3)
                                          ▼ writes
                                     screwtape store (SQLite, host)
                                          │ reads only
             ┌────────────────────────────┼─────────────────────────────┐
             ▼                            ▼                             ▼
   SATAN triage run                human (CLI, Emacs           Wormwood (future
   (pi-durable, native             review UI)                  executor: separate
    mail_* tools, D5)                                           unit, write token, D6)
             │ writes
             ▼
   digest / proposals ──▶ human review in Emacs ──approve──▶ Wormwood
```

This answers the brief's open question by removing it. No agent-reachable
process holds the token, so the agent never needs a broker that has one. The
mirror's process is the only one with credential and network authority.
Consumers get no JMAP path at all, which is narrower than the brief's
"restricted API".

It also changes the brief's operations. `mailboxes`, `list`, `read` and
`thread` become queries over the store, and the limits in brief §4.4 still
apply to their results. `changes` splits in two. Its upstream half (JMAP
`Email/changes`, `Mailbox/changes`, and `Email/queryChanges` for query
membership) belongs to the mirror. Its consumer half ("what is new since my
last run") is a cursor over the store, held by each consumer.

**The consumer cursor** (screwtape DEC-028, SL-003) is an **arrival
cursor**: `list --after <cursor>` and `read --after <cursor>` return the
messages strictly after it in `(received_at_ms, id)` order, oldest first.
The cursor is an opaque string each item carries; `""` starts from the
beginning. The consumer holds it; Screwtape keeps no per-consumer state and
needed no schema change. It suits triage, which acts on new mail and reads
current flags from the output. Known limits, stated in the Screwtape README
§ Contract:

- Mail that enters the window with an older `received_at` (late delivery,
  moved back to Inbox, a widened window) is not returned.
- Filters do not reopen passed positions: a message that starts matching
  `--mailbox`, `--unread` or `--from` after the cursor passed it is not
  returned.
- A future-dated `received_at` (settable by `Email/import`) moves a cursor
  past later real arrivals; a consumer must not store a cursor later than
  now plus a skew allowance.
- The cursor is not scoped to an account.

A consumer may re-scan a short overlap and drop ids it has seen. A change
cursor (a per-run sequence, schema v2) can be added later without breaking
this one.

Milestones 1 and 2 involve no LLM.

**Amendment (2026-10-29, screwtape SL-004): an optional classifier stage.**
`screwtape.service` (sync) still involves no model of any kind. A separate
verb of the same binary, `screwtape classify`, reads `read` output on stdin
and asks a decision model for typed answers about each message. It composes
by pipe and is not part of the mirror:

```text
screwtape read --after "$cursor" | screwtape classify   # one envelope per message
```

The model is Jev (typesafe.ai), a decision model, not an LLM: it answers a
fixed schema of questions (`mail-1`: purpose, security relevance, requested
action, deadline, deception cues, agent directive, time pressure,
substance) with probabilities. So D1's "no LLM" holds for the mirror, and
the classifier is a new outbound path with its own limits:

- Only a PII-stripped state leaves the host: subject, bodies, attachment
  types and names, and sender domains, after a best-effort regex pass.
  Names, postal addresses and short numbers survive it (screwtape README,
  "What Jev sees"). Real mail is never committed (screwtape POL-002).
- The Jev key is held like the mail token (D3), decrypted only inside a
  transient `systemd-run` unit that runs `classify` (screwtape DEC-038).
  Jev is reached through the LLM gateway (screwtape DEC-033, DEC-039).
- Nothing is persisted. Screwtape wipes its mail tables each sync, so
  classifications are recomputed per call until evaluation says otherwise.
- Output derives from attacker-controlled text. It is validated against the
  schema, advisory only, and never drives anything irreversible.

**Not RFC-019 D2.** RFC-019 D2 set aside mirroring *host* data into the
*room* (oubliette's microVM). Here, *remote* data is cached *on the host*,
and SATAN still reaches it through tools, as D2 prefers. The two do not
conflict.

**Cost.** Mail now sits on local disk as plaintext. That is new sensitive
state with a retention question (D4). Freshness is bounded by the timer
interval.

### D2: What Screwtape is

- A standalone Gleam package in a new repo, `~/dev/screwtape`, packaged and
  deployed by `~/flakes`, like satan-attrd. It has no dependency on
  pi-durable, Emacs or SATAN, and runs no daemon.
- **Gleam is a new language in SATAN's orbit.** POL-001 makes Rust the target
  for daemons; Screwtape is a oneshot, not a daemon. It sets a precedent and
  brings a new toolchain to `~/flakes`. Gleam compiles to Erlang (BEAM) or
  JavaScript. **Target: BEAM** (operator, 2026-10-26). The M3 `mail_*` tools
  (TypeScript, in pi-durable) therefore share no code with Screwtape. They
  consume an **explicit, versioned contract** that Screwtape publishes and
  tests, never its internals. There were two candidate forms (OQ-11):
  - **Read schema:** versioned SQLite views over the store. The tools read
    them in-process with no subprocess, and the tables behind the views stay
    private.
  - **CLI JSON:** Screwtape's read commands, with a schema for each output.
    Each call costs a BEAM start, but every consumer, the CLI's human users
    included, gets the same interface.

  **Chosen: CLI JSON** (screwtape DEC-027; operator assent, 2026-10-27). The
  contract is the JSON stdout of the read verbs (`mailboxes`, `list`,
  `read`, `thread`) in the versioned `{version, kind, data}` envelope;
  the tables stay private and no views are published. Reasons: one read
  surface instead of two (no parallel implementation); the table design is
  not frozen behind a public interface; pipes compose; a BEAM start per call
  is cheap at triage volumes. Compatibility (screwtape DEC-029): one version
  for the whole contract, now 1; new fields, verbs and optional flags keep
  it; removing, renaming or retyping a field, changing a meaning or an
  ordering, or adding an enum value bumps it, and consumers refuse an
  unknown version. It is documented in the Screwtape README § Contract and
  pinned by render and CLI tests, with no JSON Schema (screwtape DEC-030).

  The contract carries the brief's bounds and provenance fields, and
  Screwtape's tests assert them: `--limit` at most 500, `--max-bytes` per
  message with `output_truncated`, `thread` bounded to its last `--limit`
  entries with `total` and `truncated`, and per-body truncation recorded at
  sync time. `read --after` prints one `read` envelope per line, selected
  and read in one read transaction, so a pipe of selection and bodies cannot
  race a sync (screwtape DEC-032).

  A reader needs the screwtape binary, `--config`, and a writable store
  directory: a read-only WAL connection creates `-wal` and `-shm` beside the
  store (screwtape DEC-031). How a jailed consumer gets them is OQ-6's.

  **Composing by pipe.** The mail classifier (screwtape IDE-001) is a
  separate program over the same CLI JSON, not a Screwtape feature or a
  second interface: a tool pipes `screwtape read --after …` into it.
- A JSON CLI with stdout for data and stderr for diagnostics. `sync` is the
  verb the unit runs. Read verbs over the store serve humans and, through the
  CLI JSON contract (OQ-11), the native tools.
- **Bounded sync.** A configured window (mailboxes, date range or count),
  maximum body bytes per message (JMAP `maxBodyValueBytes`), and a page-depth
  cap. Truncation is recorded per message, never silent.
- HTML-only bodies are reduced to text at sync time, without fetching
  anything external, so no consumer ever renders HTML.
- Sync state (JMAP state tokens) lives with the store. An invalid or expired
  state (`cannotCalculateChanges`) triggers a bounded full resync and is
  logged.
- Failures leave the previous store intact, and the unit's exit status
  reports them.

### D3: Credential isolation: what holds and what does not

**Token source: 1Password, provisioned once into an encrypted credential**
(operator, 2026-10-26; screwtape DEC-001). This supersedes the first answer,
an `op://` reference resolved when the unit starts: a host test showed that
prompts on every timer run (OQ-4). The LLM gateway's pattern replaces it.
Once per token rotation the operator pipes `op read` into
`systemd-creds encrypt --user --name=fastmail`, which writes
`~/.config/credstore.encrypted/screwtape.fastmail`. Screwtape's user unit
loads it with `LoadCredentialEncrypted=` and reads
`$CREDENTIALS_DIRECTORY/fastmail`. 1Password stays the source of truth, and
`op` leaves the run-time path. `op` itself goes through the setgid wrapper
`/run/wrappers/bin/op` and the 1Password desktop app
(`~/flakes/agents/README.md` § Secrets via 1Password).

What holds:

- No cleartext token file exists at rest. systemd decrypts the credential
  into the unit's credentials directory only while a run is live. The token
  is never in argv, the environment, logs or the store.
- No timer run prompts, and none needs the desktop app.
- No consumer has a JMAP code path.
- The token is read-only, so no code path available to the mail-processing
  agent can mutate the mailbox, whichever way the gaps below are closed.

What does not hold by itself:

- **Anyone who can call `op` can read the token.**
  - On Linux the only binary check is the group: the app resets any
    connection whose GID is not `onepassword-cli`.
  - The socket is open to "any process started by this user".
  - Authorisation is then scoped to a terminal session, not to a calling
    binary: "an ID that's based on the current `tty`, plus the start time"
    (1Password, *app-integration-security*; screwtape SL-001 research,
    2026-10-26).
  - So any same-uid process that can run the setgid wrapper is authorised
    by the same approval as the operator's own `op`.
  - The `op` wrapper and the app's sockets must therefore stay out of every
    jail that holds model output.
  - `check-jails` (`justfile`) asserts it with `op-unjailed` (screwtape
    DEC-013), shaped like `runner-socket-unjailed`. It scans every jail
    launcher, the scripts it execs, its `--args` files and the nested jail
    launchers on its PATH. It forbids the `op` wrapper, `onepassword-cli`,
    `.1password`, the app's socket names, and any bind of an ancestor that
    would expose them (`/`, `/run`, `/run/wrappers`, `/run/wrappers/bin`,
    `/run/user`, `/run/user/<uid>`). A synthetic `--ro-bind /run /run`
    launcher is its positive control. It guards known paths; it is not
    proof of NF-004.
  - One of the app's sockets, `@1PASSWORD_SDK_INTERGATIONS`, is in the
    abstract namespace. A jail reaches abstract sockets whatever it binds,
    unless it has its own network namespace. RSK-021 owns the probe that
    the GID check refuses it from inside a jail.
- **The decrypted credential.** While a run is live, the token sits in the
  unit's credentials directory under `$XDG_RUNTIME_DIR`, readable by the
  operator's processes. That is accepted under the threat model below. No
  jail may bind `/run/user/<uid>` (`op-unjailed`).
- **The plaintext store.** Any unjailed process running as `david` can read
  it, including the malebolge runner, which RFC-019 D6 notes is an unjailed
  unit. Native mail tools confining themselves to the store is a property of
  their code, not something the OS enforces. A jail whose working directory
  is or contains the store, the credential or `~/.config/systemd/user`
  exposes them (screwtape SL-001 design I7; `~/flakes` IMP-042; ISS-028).
- **Host coding tools.** The interactive daemon's host bash reaches whatever
  its jail binds (ISS-028).
- **Provisioning.** `op read` raises a PolKit prompt (the desktop's
  system-authentication dialog), and approving it while the app is locked
  unlocks the whole vault. The operator runs it by hand once per rotation,
  so this is an interactive act, not a timer's.

**Same uid** (screwtape DEC-016, DEC-017). Screwtape runs as a Home Manager
`systemd --user` oneshot under `david`. Its store sits in its 0700
`StateDirectory` (`~/.local/state/screwtape/`), inside the `$HOME` that jails
shadow. The operator's threat model: jails are the safety boundary, and
unjailed processes running as `david` are trusted. They already reach the
same mail through other clients. A dedicated uid would add little against
them and would need a sanctioned read path; humans and M3 tools open the
store directly.

### D4: Three outputs, three decisions

The operator wants two kinds of output: help managing mail, and write-ups of
the most interesting unread mail. Each artefact gets its own decision, with
state as the starting point:

| Artefact | Writer | Readers | Starting root | Open |
|---|---|---|---|---|
| Raw mail store | Screwtape | native tools, CLI | Screwtape's state dir (`~/.local/state/screwtape/`), SQLite | retention (OQ-10) |
| Operation proposals | SATAN triage run | human (Emacs review), Wormwood | `~/.local/state/satan/…` | schema (D6); lifecycle after approval |
| Unread digest | SATAN triage run | human | `~/.local/state/satan/…` | corpus vs state vs Org inbox feed (OQ-5) |

The raw store belongs to Screwtape, not to SATAN, so it sits under
Screwtape's own state directory, the way panopticon's store is not a SATAN
root.

**SQLite, not Postgres.** Screwtape has a single writer and a single host,
and its store can be thrown away and rebuilt by resync. malebolge and the
runner store their data the same way. Postgres would add a server dependency
to a oneshot. Would Belphegor ever need to "link up" with satan-attrd's
Postgres? The likely link is a signal: mail volume or an unread backlog as
an attribute input. Signals reach attrd through its outcome inbox (a
producer enqueues), not through a shared database. So linking needs a
producer, not a co-located store, and SQLite does not rule it out. A join
across mail and attributes would be the case for Postgres; nothing proposes
one.
Digests and proposals are SATAN's output, and state is discardable. Promoting
either to the corpus later would make it versioned, model-facing text, so the
question stays open.

Mail-derived text must not become authoritative memory or configuration
(brief §4.2). Neither output feeds `hippocampus_*` or `memory_*` without
separate approval.

### D5: SATAN reads mail through native tools in a restricted run

- `mail_*` read tools are pi-durable native tools (RFC-019 D6) over the
  store, confined to it and bounded per brief §4.4. They do not go through
  satan-mcp.
- They are not added to the interactive daemon's tool set. That session has
  host bash, so brief §4.3 ("no arbitrary shell") cannot hold there.
- Triage runs as its own invocation with a fixed tool set: `mail_*` reads plus
  one writer for its output. The tool set comes from configuration; mail
  content cannot widen it. Where the invocation lives (a runner job kind, a
  separate timer, or a mode under RFC-018 D4's "modes as events") is open
  (OQ-6).
- **Pre-classified subset (amendment, 2026-10-29).** `mail_*` results may
  carry `classify` answers, so triage can read a pre-classified subset first.
  A classification is advice: it does not widen the tool set, replace a
  message's claims-versus-facts split, or authorise a proposal. The
  deception and agent-directive scores are hints against injection (RSK-002),
  not a defence. Whether results reach SATAN at all waits on the operator's
  evaluation of Jev's answers on real mail (screwtape IMP-003). Tool side:
  malebolge IMP-022.
- Each digest entry carries the brief's evidence fields: summary, priority and
  why, next action, any explicit deadline, confidence, and source message and
  thread ids. It keeps an email's claims separate from verified facts.

### D6: Wormwood and approval (future)

The brief's design carries over (§6): a declarative, versioned plan; ids
scoped to an account; the expected source state per operation; approval bound
to the canonicalised plan; per-operation accept or reject; no replay; and
stronger checks for unsubscribe and rules. Locally:

- Wormwood is its own unit with its own write token (its own `op://` ref) and
  no route from the agent. It is a separate binary from Screwtape (POL-001:
  one binary per extraction). It may share Screwtape's JMAP and model
  modules as a library.
- Emacs is the review and approval surface (ADR-017). It reads proposals and
  records approvals, but holds no credential and runs no process.
- Before acting, Wormwood rechecks state live over JMAP, not against the
  store, because the store may be stale.
- The schema is defined at milestone 4. Fastmail rule management is
  researched separately: JMAP Mail has no portable rules API.

### D7: Authority ledger

If Screwtape is in SATAN's orbit, these are authority items under ADR-017
§3, each with one owner:

| Proposed row | Item | Owner | Enforced at |
|---|---|---|---|
| 10 | Mail read credential custody | `screwtape` (new token) | user-scoped `systemd-creds` credential, provisioned once from 1Password and loaded by Screwtape's user unit (`~/flakes` `features/satan/screwtape.nix`); `check-jails` `op-unjailed` (no `op` wrapper, 1Password socket or exposing `/run` ancestor in any jail) |
| 11 (future) | Mail write credential custody | `wormwood` (new token) | Wormwood's unit |
| 12 (future) | Mail-plan approval | `emacs-client` | the Emacs review surface |

ADR-017 ledger INV-2 requires each row to cite a SPEC-001 requirement or a
governing ADR. SPEC-001 has no secret-custody requirement (RFC-018 D3), so
row 10 needs one or an ADR stand-in. The alternative is RFC-018's precedent
for provider keys (DEC-049): a credential no SATAN surface holds leaves the
ledger's inventory. Screwtape is outside SATAN, so that precedent arguably
applies (OQ-2). The operator's current view: probably add the row.

### D8: Sequencing

1. **M1: mirror, full bounded sync.** The unit, the token, the store, the CLI
   read verbs, mocked-JMAP tests, then one live run against the real account
   with the read-only token. Acceptance: a bounded set of real messages lands
   in the store, and the mailbox is unchanged. **Slice: screwtape SL-001** (`~/dev/screwtape`), after its CHR-001 flake bootstrap.
2. **M2: incremental sync.** Upstream half only (D1). `Email/changes` from
   the stored Email state picks which stored messages get a light refresh
   (`mailboxIds`, `keywords`). `Email/query` still decides which messages are
   in the window, and runs only when something changed. Retention
   (`retain_messages`) is separate from the fetch window (partly answers
   OQ-10). A run falls back to the M1 full sync when there is no stored
   state, on `cannotCalculateChanges`, when the window changed, or when there
   are too many change pages. Each run reports `mode` and `fallback_reason`.
   No duplicate body fetches: an unchanged account sends no `Email/get` with
   ids. `Email/queryChanges` and `Mailbox/changes` were not needed. The
   consumer cursor stays with M3 (OQ-11). **Slice: screwtape SL-002**, done
   2026-10-27; live check: consecutive real syncs took the incremental path.
3. **M3: SATAN triage.** (The `classify` verb, an optional pre-classifying
   stage, is **screwtape SL-004**, done 2026-10-29; its evaluation on real
   mail is screwtape IMP-003; wiring it into the tools is malebolge IMP-022.)
   Native `mail_*` tools, the restricted invocation, the
   digest, and prompt-injection cases. The contract they consume (OQ-11) and
   the consumer cursor (D1) are screwtape SL-003.
4. **M4: proposals.** Schema, validator and preview, with no execution. The
   Wormwood comes after M4.

M1 and M2 stay separate (OQ-7, settled): the M1 schema carries JMAP state
tokens from the start.

| Brief | Here | Why |
|---|---|---|
| CLI or library invoked by the agent or a broker | Scheduled mirror; consumers read a store | Operator direction; removes the broker question (D1) |
| "Thin pi extension" | pi-durable native tools in a restricted run, not in the interactive session | Host bash in interactive SATAN (D5) |
| TypeScript | Gleam | Operator choice (OQ-1) |
| Unnamed components | Belphegor, Screwtape, Wormwood | D0 |
| Read-only token, storage unspecified | Provisioned once from 1Password into a user-scoped encrypted credential | Operator; LLM gateway precedent (D3) |

| Digest as Org text | Org text, home open | Three-roots rule; separate decisions per artefact (D4) |
| No model before SATAN sees mail | Optional piped `classify` verb (Jev, a decision model) over PII-stripped state; the mirror stays model-free | Operator direction, 2026-10-27 (screwtape IDE-001, SL-004) |
| Reviewer unspecified | Emacs as review UI only | ADR-017; operator direction |

  - **Host test, 2026-10-26:** a `systemd-run --user` unit with no tty
    gets a prompt and succeeds once approved. An immediate second unit
    prompts again, so `op` at unit start would prompt on **every** timer
    run.
  - **Local precedent:** the LLM gateway (`~/flakes`
    `features/agents/gateway/`) resolves `op` once, when the operator runs
    `just gateway-credentials`.
    - That command pipes `op read` into
      `sudo systemd-creds encrypt --with-key=host+tpm2` and stores the
      result in `/etc/credstore.encrypted/`.
    - Its system unit runs as a static uid with `LoadCredentialEncrypted=`.
    - There is no prompt at run time and no cleartext or bootstrap secret,
      and 1Password stays the source of truth.
  - **Chosen** (operator, 2026-10-26): that precedent, adapted to a user
    unit: `systemd-creds encrypt --user` and the operator's uid, not
    `--with-key=host+tpm2` and a static uid (screwtape DEC-001, DEC-016).
    With `op` off the run-time path, the host tests above no longer gate
    anything.
  - **Set aside:** a dedicated `screwtape` uid owning the store (screwtape
    DEC-002, superseded by DEC-016); a 1Password service account, whose
    token is a bootstrap secret on disk and which cannot read the Personal
    vault; resolving the token once per login into a 0600 file on tmpfs.
  - **`check-jails`** now carries `op-unjailed` (D3; screwtape DEC-013).
- **OQ-5: digest home.** State, corpus, or an Org feed the user reads.
- **OQ-6: where triage runs.** A runner job kind, its own timer and unit, or
  a mode-as-event (RFC-018 D4). It depends on RFC-019 OQ-1 (one process or
  two) and OQ-2 (patch mode's tool set).
- **OQ-9: facts to verify before design.** Fastmail: the read-only token
  scope and its exact capability URIs, the session endpoint,
  `Email/queryChanges` support, rate limits and request caps
  (`maxObjectsInGet`, `maxCallsInRequest`). Gleam: whether a JMAP client
  exists (brief §11 asks), the SQLite and HTTP libraries for the chosen
  target, HTML-to-text, and Nix packaging.
  - **Largely answered** by screwtape SL-001 research, 2026-10-26.
  - **Fastmail:**
    - The session URL is `https://api.fastmail.com/jmap/session`, with
      `Authorization: Bearer`.
    - A separate "Read-only access" JMAP token scope exists. How it combines
      with "Email" is undocumented.
    - The listed capability URIs are `urn:ietf:params:jmap:{core,mail,submission,vacationresponse,contacts}`
      and `https://www.fastmail.com/dev/maskedemail`.
    - Fastmail documents no numeric request caps or rate limits ("there are
      rate limits in place"), and does not document `Email/queryChanges`
      support. Screwtape must read caps from the live session, and
      `canCalculateChanges` from each query response.
  - **Gleam:**
    - No Gleam or Erlang JMAP client exists, so Screwtape needs a thin
      hand-written one.
    - The libraries are `gleam_httpc`, `gleam_json`, `sqlight` (over the
      `esqlite` C NIF, a native Erlang extension) and `htmgrrrl`.
    - Packaging: `nix-gleam` with rebar3's `pc` plugin, shipped as an
      erlang-shipment, not an escript, because of the NIF.
    - Still to prove: an offline build and `gleam test` under
      `nix flake check`.
- **OQ-10: retention.** How much mail the store keeps, and whether bodies age
  out before metadata.
  - **Partly answered** by screwtape SL-002 (2026-10-27). An optional
    `retain_messages`, which requires `max_messages` and is at least it,
    keeps that many messages, newest first, in the configured mailboxes.
    Unset, the store holds exactly the fetch window. Still open: retention by
    age, and bodies ageing out before metadata.
