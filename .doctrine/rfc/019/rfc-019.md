# RFC-019: One malebolge agent: the room is SATAN's machine, the host is reached through SATAN's tools

## Context

RFC-018 D4/D5 step 4 sketched the *habitat*: durable SATAN in a microVM, with
"high autonomy inside the habitat; very little authority outside it". Its
spike finding F5 named the mechanism (pi-env: harness on the host, tools in
the VM). SL-023 has since built half of it: `satan-runner` runs patch jobs
with the model loop on the host and the coding tools in oubliette room
`assistant` over pi-env (`~/dev/malebolge` `src/runner/env.ts`). The other
half did not move. Malebolge today is two agents with opposite reach:

```
 interactive daemon (jailed-malebolge)        satan-runner (patch jobs)
 bwrap jail ON THE HOST                       model loop on host, tools IN THE ROOM
 cwd = launch dir = ~/notes, rw               room: no uplink; /work persistent clones
 network on (specDev profile)                 coding tools over ssh (pi-env)
 coding tools on the host                     no SATAN MCP tools (start.ts:147)
 + every SATAN MCP tool (union, "interactive")
```

Forces:

- **Inverted against intent.** The agent with freedom (interactive) runs on
  the host with network and host coding tools. The agent in SATAN's own
  machine (jobs) gets only one-shot, path-allowlisted, perception-less jobs.
- **Live defect.** `just hello-durable` launches the jail in `~/notes`, and
  every jail binds its launch dir rw (`~/flakes/SATAN.md` § Jails), so the
  interactive daemon's coding tools can write the user's notes. That breaks
  the three-roots rule (notes are read-only to SATAN).
- **No mounts into the room.** Firecracker supports no shares
  (`oubliette/vm/common.nix:7`), so RFC-018's "read-only evidence mounts"
  cannot be built as mounts. Host data reaches the room only through the door.
- **The room is already a persistent machine.** Root fs is tmpfs, but `/home`
  and `/work` are persistent volumes, and rooms have no `reset-home`
  (`oubliette/vm/room.nix`). The runner's post-collect clean resets only the
  job clone's working tree; no branch is deleted or moved (`room.ts:423-425`,
  `prepare.ts:67-83`).
- **Host reads already exist as tools.** `notes_*`, `activity_read`
  (panopticon behaviour), `content_read` (web pages and digests),
  `hippocampus_*`, `vcs_log` run in Emacs. SATAN's own run logs and tick
  traces (`~/.local/state/satan`) have no tool.
- **Commit lag.** `capsule push` sends the host checkout's
  `refs/heads/<branch>` (`oubliette/host/room-git.nix:189`), so the room sees
  the last local commit, and only when a job refreshes that repo. `~/notes`
  and `~/satan-corpus` are committed (`just commit`) when the user remembers.

## Discussion

### D1: One agent, two modes, composed tool layers

```
               malebolge agent (model loop on host; gateway key stays on host)
                 │
   ┌─────────────┴─────────────────────┬──────────────────────────────┐
   │ SATAN MCP tools                    │ coding tools                  │
   │ run in Emacs; host reads;          │ read/write/edit/bash,         │
   │ filtered per mode                  │ always IN THE ROOM (pi-env)   │
   └────────────────────────────────────┴──────────────────────────────┘
     mode vm     cwd /home/agent; persistent; no job
     mode patch  cwd /work/<repo> on job/<id>; + guard, collect,
                 patch_job_* semantics (SL-023/SL-025 contract unchanged)
   removed: host coding tools, host network (the jailed pi/malebolge
            interactive profile)
```

The layers exist: `env.ts` (room execution), `src/satan-tools.ts` (MCP
bridge), Emacs mode specs (per-mode tool allowlists). The proposal composes
them; it builds no parallel implementation. Pros: one mental model; the
`~/notes` rw defect disappears; the room becomes the habitat RFC-018 asked
for. Cons: no web access from SATAN's coding tools (see OQ-5); the runner gains
a dependency on satan-mcp (OQ-3).

### D2: Host reads go through tools, not a mirror

A host-to-room `rsync` mirror (allowlisted paths, owned by a separate room
user) was considered and set aside. With MCP tools in both modes, host reads
are live and already scoped. Cost: raw `grep`/`jq` over the data is replaced
by fixed tool scopes. Gap: a read tool over `~/.local/state/satan` (run
bundles, tick traces), which doubles as the self-log reader (D4). Revisit the
mirror only if tool scopes prove too narrow.

### D3: Room conventions between the modes

Both modes are the room user `agent`. A vm-mode edit in a `/work` clone makes
the next job on that repo fail `dirty_clone`. Rule: vm mode works under its
home and clones from `/work` when it needs a repo. `dirty_clone` already
detects violations, so this is a convention, not new enforcement. In-room git
is unguarded (`stash`, `reset --hard` allowed); the boundary stays collection's
classification plus human review, which answers RFC-018 OQ-3 for this habitat
(in-VM git, host-side check at collect).

### D4: Self-log instrumentation

The pi-durable session store already records every turn. What is missing is
SATAN reading its own history. Default: a read tool over SATAN's state (D2's
gap), not an agent-written journal.

### D5: Commit freshness

`just commit` in `~/notes` and `~/satan-corpus` on an hourly user timer (and
optionally a debounced watch), owned by `~/flakes`, not the runner. Before a
refresh, the runner may run one configured pre-refresh command, which knows
nothing of either repo. Under D2, notes reads are live, so freshness matters
chiefly for `~/satan-corpus` (the base of `self-edit-mind` jobs).

### D6: Tools that do not need Emacs become pi-durable native tools

Many SATAN tools read files or run a program and use nothing only elisp has.
POL-001's earns-the-seat test ("does it use the editor as an editor?") says
they do not belong in Emacs; ADR-017 says Emacs is a client. Ported as
pi-durable tools (`defineTool`), they run in the agent process, need no
satan-mcp, and work with Emacs absent, which shrinks OQ-3 to the tools that
stay. Rough split, to verify per tool (OQ-8):

| likely native | likely stays in Emacs |
|---|---|
| `activity_read`, `content_read` (panopticon files) | `org_read_context`, `org_update_owned_block` (org) |
| `notes_recent`, `notes_grep`, `notes_read` (fd/rg, root-confined) | `notes_at_satan_*` (if they parse org/denote) |
| `hippocampus_*`, `motive_read`, `docs_*`, `vcs_log` | `memory_*`, `inbox_append`, `proposal_stage` (logic lives in elisp) |
| `notify_send`, `sway_*`, `speak` (one program each) | `patch_job_*` (Emacs stamps the run's mode, ledger rows 1-2) |
| the new state reader (D2, D4) | `goad_ask` |

Two constraints:

- **No parallel implementation.** Broker-spawned runs (tick, morning,
  `@satan`) still call the elisp tools. A port is a move only once those runs
  also go through malebolge (RFC-018 D4: modes as events); until then a ported
  tool exists twice. Sequence ports behind that, or port only tools no broker
  mode allowlists.
- **Native tools run on the host, in the agent process.** The runner is an
  unjailed unit, so a native read tool there reaches whatever its code allows:
  each must confine itself to its root, as `notes_read` does, or the process
  must run in a jail with read-only binds.

### D7: A coding layer in malebolge

pi-durable's tools share the coding agent's lineage (`edit-diff.ts`,
`file-mutation-queue.ts`, `path-utils.ts`; same four defaults). The coding
agent's strength over it is mostly prompt. Compared at
`~/.local/src/pi` (`packages/coding-agent/src/core/system-prompt.ts`):

| part | pi coding agent | malebolge today |
|---|---|---|
| preamble + rules (concise, paths, per-tool guidelines) | yes | persona only |
| project context (`AGENTS.md`/`CLAUDE.md` up the tree) | yes | no |
| skills | yes | yes (`skills.ts`, DEC-067) |
| cwd section | yes | no (daemon) |
| `bash` timeout parameter | yes (`bash.ts:42`) | no |
| `grep` (ripgrep, `--json`), `find`, `ls` | optional tools | none; bash only |

Proposed: one malebolge extension carrying the missing sections (coding
rules, project context, cwd), a `bash` timeout, and a `grep` tool. Each is a
pi-durable section or tool. Two constraints:

- **Through the environment.** pi's `grep.ts` spawns a local `rg`
  (`child_process.spawn`, `ensureTool("rg")`). A port must run `rg` through
  the call's `ExecutionEnv` (`env.exec` with an argv), so it works in the room
  over pi-env. The room has `rg` and `fd` (oubliette `fragments.nix` extra
  `search`, selected by `rooms.assistant`).
- **Project context is read in the environment too.** In patch mode,
  `AGENTS.md` comes from the job's clone in the room, not the host checkout.

Shared by both modes; the persona stays SATAN's, and the coding layer sits
beside it.

## Outcome

Open. Proposed: D1 (one agent, modes vm and patch, host coding tools and
network removed), D2 (tools, not mirror), D3 (convention), D4 (state read
tool), D5 (timer in `~/flakes`), D6 (Emacs-free tools ported to pi-durable),
D7 (coding layer: prompt sections, bash timeout, grep). Open questions:

- **OQ-1: one process or two.** The runner is a unit built from the pin; the
  daemon runs from the working tree. Proposed: share the tool composition now,
  keep two processes until a reason to merge appears.
- **OQ-2: patch mode's SATAN tool set.** "All usual tools" includes writers
  (`hippocampus_write`, `motive_replace`, `notify_send`, `speak`) and
  `patch_job_create`, so a job could submit jobs. Needs a patch mode spec:
  reads plus hippocampus at most; never `patch_job_*`.
- **OQ-3: how a session's mode reaches satan-mcp.** `satan-mcp--tools-call`
  resolves the fixed mode `"interactive"` (`satan/satan-mcp.el:289-307`), and
  the socket has no authentication, so a client-declared mode is not a
  boundary. Candidates: a socket per mode; or the runner (host-side, holder
  of the job) filtering the tool list from its config. ADR-017: the runner
  must keep enforcing with Emacs absent; jobs then lose SATAN tools, which is
  degradation, not failure.
- **OQ-4: deprecation inventory.** Before removing the host profile: goad
  backend writes (`~/satan-corpus/goad`, rw in the jail today), the goad skill
  and tools, `~/notes/.pi/extensions/satan.ts` and its users.
- **OQ-5: network.** The room has no uplink. Is a host-side, read-only web
  tool (fetch/search via MCP) wanted, or is `content_read` over visited pages
  enough?
- **OQ-6: naming against SL-025.** SL-025 DEC-068 stamps MCP-session submits
  as mode `interactive`; under D1 that is the vm mode. Rename or keep.
- **OQ-7: governance.** Whether D1 needs an ADR-018 amendment (topology:
  where execution lives) and a SPEC-002 revision (containers and arrows).
- **OQ-8: per-tool port audit.** For each tool: what it needs only Emacs for,
  which broker modes allowlist it, and its confinement root once native. The
  D6 table is a first guess, not a finding.
- **OQ-9: is malebolge a good enough coding agent?** Evidence before pi's
  interactive profile is deprecated (D1): run the same cases from pi's
  `packages/evals` (vitest-evals) against the coding agent and against a
  malebolge-shaped harness (D7 layer, room environment, the deployed model).
  Also weigh pi-durable's API churn ("Experimental. The API changes without
  notice"; malebolge pins 1.3.0).
