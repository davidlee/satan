## Context

The attribute layer is SATAN's metabolism: eight global control variables —
Curiosity, Hunger, Suspicion, Doubt, Cruelty (`friction`), Shame, Brooding,
Metamorphosis — that are supposed to bias behaviour and never expand permissions
(`docs/attributes/design-contract.md` §1; the phrase originates in `docs/attributes.brief.md`
§0, which is the origin brief, not a specification — see the docs ledger). It is also the
part of the ecosystem that has been
touched least in the last months, is hardest to approach, and — by its own design
intent — is not yet doing the thing it was built for.

This RFC exists because that state is spread across two repos: the daemon
(`satan-attrd`, Rust, 4,521 lines, 14 modules, 6 migrations) and the broker wiring
(`satan/satan-attribute*.el`, 749 lines) plus a 2,883-line documentation corpus whose
*authoritative* half lives in the broker repo while the code lives in the other one.
Understanding it requires reading both, and the entry documents in the daemon repo
are six months stale. That is the approachability problem, stated plainly.

What has changed since the last whole-system look (RFC-016, 2026-07-06):

- Cognition is no longer dormant: ticks run on the gateway `deepseek-flash` profile
  (ISS-012 resolved), so the metabolism now has a live consumer of its capsule.
- `ignored` exists as an observer verdict, so the outcome axis is no longer
  positive-only.
- Decay is not "deferred" any more: T-attr-2c..2f landed 2026-05-29 with 107 tests
  (hourly check, daily fire, `maintenance:<utc-day>` synthetic run-ids, seq resume).
- The goad-ask surface (SL-016) and the `reading` sensor reason (IMP-055) both
  extended the daemon — the layer is *maintained*, just never *consumed* differently.

### 2. What actually moves

Per `wiring-status.md` (updated 2026-10-26 — the freshest doc on this side):

- **Active:** Curiosity (sensor `segment_backlog`, hippocampus `trace_marked`),
  Hunger (outcome `worked`, sensors `typing_active`/`reading`/`typing_idle`),
  Doubt (every non-neutral outcome), Shame (widest coverage), Brooding (outcomes +
  hippocampus writes), Metamorphosis (contradicted/harmful).
- **Near-dormant:** Suspicion — needs the reserved `resonance` source; today it has
  one small positive (`searched`) against one global negative (`contradicted`).
- **Structurally locked at 0:** Cruelty/`friction` — no implemented source produces a
  positive delta, *and* the cap `friction ≤ max(0, 1 − doubt − shame)` clamps to 0
  whenever doubt + shame ≥ 1.0. Doubt and Shame are decay targets, so headroom accrues
  ~0.02/day in quiet periods — and one `harmful` outcome (+0.30 to both) closes it again.
  Cruelty can rise only in good weather; the positive source still does not exist.
- **Reserved, unwired:** `percept`, `resonance`, `tool_error`, `manual`.

So roughly three of eight variables can move, and the one that expresses adversarial
edge cannot move at all.

**Homeostasis is not universal — and it excludes the attributes a gate would read.**
Decay covers exactly `[shame, doubt, brooding, metamorphosis]` (`decay.rs:64-72`, which
names Curiosity, Hunger, Suspicion and Friction as excluded by design). The two most
plausible inputs to a discretionary-arrival gate are Curiosity and Hunger, and both are
undecayed. Their saturation is a function of the **counter-delta rate**, not of decay:

- Curiosity: `+0.05` per emitting `segment_backlog` event against `−0.025` per
  `trace_marked` — cancellation needs two marks per emitting tick.
- Hunger: `+0.05` per `typing_active` tick against `−0.05` per `worked` outcome
  (`0.025` for `reading` / `typing_idle`) — cancellation needs one worked intervention
  per emitting tick.

Absent those rates the values clamp at 1.0: from zero, 36 emitting ticks at +0.05 is
+1.8/day — **illustrative only**. 36 is the 40-minute cadence (ISS-022), the emitting
condition is a non-empty backlog per tick, and no runtime rate has been measured. The
defensible claim is conditional — saturates when the counter-delta rate falls below the
channelling rate — and it is measurable from `satan_attribute_events`.

### 3. Findings — where it hurts

Ordered by how much they cost right now, not by how interesting they are.

**F1 — A signal is destroyed on every tick, irreversibly. (bleeding)**
`satan-sensor-content` enqueues `reason: "content_backlog"` (`satan-sensor-content.el:122`);
the daemon's sensor reason set has no `ContentBacklog`, so `parse_inbox_payload` fails
and `process_outcome_row` **deletes the row** and logs one error line
(`run_loop.rs:527-548`). The broker advances the content probe watermark on *enqueue*,
not on acknowledgement (`satan-sensor-content-probe-commit`), so a rejected event is
unrecoverable: the evidence is consumed, and nothing in the database records that it was
ever enqueued. ISS-011
records 22 rejections in 3 days as of 2026-09-14, i.e. ~7/day since at least 2026-09-11;
nothing in either repo's history suggests it was fixed. **[verify]**

RFC-016's Phase 0 recorded the same rows as a *poison message* blocking startup. The
current code deletes them on parse failure, which traded a stuck queue for invisible
data loss. Both states are wrong in opposite directions; the correct one is in F2.

**F2 — Forward compatibility is a human convention, not a contract.**
Only the payload *major* version is checked (`rpc::check_schema_major`). An additive
reason is indistinguishable from garbage, so an older daemon drops a newer broker's
signal. Three reasons have been added since September (`ask_suppressed`,
`ask_uncorrelated`, `reading`), and each time the rollout rule was prose: "attrd must
be redeployed before the broker emits it" (`design-contract.md` §16, 2026-09-24;
`wiring-status.md`, 2026-10-26). One deploy done out of order is a silent,
unrecoverable loss — F1 is exactly that failure, with timestamp.

**F3 — A transient database error permanently claims an outcome.**
`process_outcome_row` sets `claimed_at = NOW()` first, then does `read_projection` and
the dispatch. Any error after the claim leaves the row claimed forever; `drain` only
selects `claimed_at IS NULL` (`run_loop.rs:456-470`). There is no retry, no expiry, no
dead-letter table. Parse/schema failures are deleted (F1); everything else can silently
vanish mid-flight.

**F4 — Three switches, two truths.**
`attribute-updates-enabled` is (a) a broker defcustom forwarded in every outcome
payload, and (b) mirrored by a variable-watcher into `satan_attribute_settings`, which
(c) the daemon's decay scheduler reads at tick start. Plus
`satan-attribute-listener-enabled` for the transport. The watcher only fires on `set`,
and the capsule hides values based on the *defcustom*, while decay obeys the *row*. A
`setq-default`, a non-`set` mutation, or a settings write that fails silently (it is
swallowed: `satan-attribute--on-enabled-change`) splits the two truths with no alarm.

**F5 — Two migration lineages on one database. (RSK-015, open)**
Broker migrations are `0001..0009` tracked in `schema_migrations` (elisp runner); daemon
migrations are `0007..0012` tracked by `sqlx::migrate!` in its own table. Two different
`0007`s now name two different things in one database (`patterns` vs `attributes`). The
runners do not collide today; an operator reading the DB cannot tell which lineage a
number belongs to, and the next person to add `0010`-something picks a side by accident.
The arrangement is possible because the store has no owner: `SPEC-002` asserts "single schema
owner per store" as a system invariant while its own container table leaves the Shared
database row's `Spec` column empty. Two lineages are the *symptom*; the gap the census found
(`IMP-067`) is that no spec names who owns `satan_memory`.

**F6 — The docs are in the wrong repo and some are lies.**
The normative contract (`design-contract.md`, 940 lines) and every theme doc live in the
broker repo; the code lives in the daemon. The daemon's own entry points are stale:
`README.md` says "**Scaffold only**" and points at `~/.emacs.d/docs/satan/…`, a path
that has not existed since the extraction; `HANDOVER.md` (2026-05-23) still describes
T-attr-1c as the next step, five months of work ago; `.doctrine/` there contains stock
memory only — no backlog, no slices — and the real history sits in `.spec-driver/`,
which doctrine marks deprecated. Meanwhile the *broker's* `wiring-status.md` asserts
"No decay implemented (§8)" and "Shame accumulates monotonically" while decay has been
shipping since 2026-05-29. Every attempt to approach this side starts by being
misinformed.

**F7 — Nothing can explain a value.**
`satan_attribute_events` is the append-only truth, and the only reader is `rebuild`.
Neither the model nor the operator can ask "why is Doubt 0.62" and get
`(reason, delta, ts, evidence)` back. The capsule shows eight bars and eight numbers
(`satan-attribute-render.el`), which is a display of a state whose derivation is
invisible. This is the main reason the layer *feels* opaque to work on: there is no way
to read it back except by SQL.

> **Durability caveat (2026-11-06).** "Truth" here means *derivational* truth: the
> projection is recoverable from the log, but the log is recoverable from nothing. `ISS-065`
> established that the host database `satan_memory` — the only copy of these events — has
> **no backup**, and that the jail database's 30-day `pg_dump` archive covers a *different*
> database (the two are unrelated, not tiers of one). So `rebuild` protects against a
> projection bug, not against disk loss, deletion or corruption. Until the store is backed
> up, "append-only" is a claim about ordering, not about survival — and Q1's "does the
> daemon earn its seat" should weigh an unbacked append-only log holding the whole outcome
> history.

**F8 — The only wired consumer is prose.**
Attributes enter the capsule and bias nothing. No gate reads them, no mode is chosen by
them, no budget is shaped by them; the tank renders them too but is unwired. Prompt
exposure is nonetheless real and universal — every mode builds its prompt through
`satan-context--finalize-prompt` (`satan-context.el:458-467`) — which makes *exposure* a
question independent of *whether anything acts on it* (see O5b). The intended
consequences live in unfrozen/undone work: IMP-012 (arrival gate, 2026-05-30) and the
frozen-corpus ADR-002 (metabolic arrival gating, "proposed, blocked" per RFC-016). Until
one is accepted, the layer is a well-tested display of eight numbers — and the honest
question is whether that earns its architecture (POL-001's earns-the-seat test).

### 4. Opportunity — what would make this side fulfilling

- **O1 — Make loss impossible, not just unlikely.** One rule with three parts: unknown
  `(source, reason)` pairs are *stored opaquely*, never deleted; failed dispatches go to
  a dead-letter with the error; claim expiry so a crash cannot orphan a row. Small, and
  it converts every future vocabulary skew from data loss into a visible backlog. The
  broker half of the same rule: advance a probe watermark on acknowledgement, not on
  enqueue, wherever the sink can reject.
- **O2 — Give the loop a vocabulary handshake.** A daemon-advertised capability set (or
  a `satan_attribute_settings` row carrying the accepted reason set) that the broker
  consults before emitting, so "redeploy attrd first" stops being folklore. Cheap once
  O1 makes the failure visible — and it *follows* O1 rather than leading it: no-silent
  loss is the higher invariant, and a handshake is a convenience on top of it, not a
  substitute. Once O1 stores unknown reasons opaquely and O3 surfaces dead-letters, O2
  may be redundant; decide after O1, not before.
- **O3 — Build the "why" reader, and make it carry health, not just history.**
  Two tiers. *Provenance*: last N events per attribute with
  `(ts, source, reason, delta, old→new, evidence)`, as a capsule line and an operator
  command. *Ingestion*: per-`(source, reason)` last-seen against expected cadence;
  `last_decay_at` and `days_since_last`; inbox depth; claimed-orphan count; dead-letter
  count.
  The second tier is not polish. **Ingestion health is unobservable from the database
  today** — parse/schema rejects are deleted (`run_loop.rs:540,548`), successes are
  deleted too (`:624`), and `satan_audit_replies` covers only broker-side validator
  rejects. A reader over successful events would have reported this layer as healthy
  throughout F1. So O3 **depends on O1**, or it degrades into reading journald — a worse
  artefact for the same information.
- **O4 — Collapse the switches to one truth.** The settings row is the authority; the
  defcustom is its UI; the capsule renders from the same row (it already reads the
  projection directly). Delete or hard-reject the divergent paths. Include the listener
  switch in the same story.
- **O5 — Decide two things, not one.** They are orthogonal, and conflating them is how
  "make it telemetry" gets mistaken for settling the prompt.
  - **O5a — Scheduling authority.** *Consumer*: accept an arrival/gating surface
    (IMP-012's shape, ADR-002's intent) so metabolism decides when and how SATAN arrives —
    the fulfilling version, and the one RFC-016's diagnosis argues for. *Telemetry*:
    declare the layer an observability surface, drop the daemon-shaped ambitions (or fold
    it into the observer per IMP-009's family), stop tuning deltas nobody acts on.
  - **O5b — Prompt exposure.** The bars are in every prompt regardless of O5a, so decide
    explicitly: *measure* (needs a replay harness — a slice, not a chore: IMP-066),
    *remove* (one branch — `satan-attribute-render-block` already suppresses on a nil
    snapshot, `satan-attribute-render.el:117`), or *keep* deliberately and stop
    relitigating. Under telemetry the cheap correct move is to decide exposure, not
    experiment on it.
  Everything else on this list is worth doing under either authority answer; the
  delta-tuning and reserved-source work is only worth doing under *consumer*.
- **O6 — Unlock the locked.** `resonance` → Suspicion is the canonical trigger and the
  cheapest unlock (the percept already computes cue handles every tick). `tool_error` →
  Metamorphosis/Doubt is next. Cruelty needs a positive source *and* relies on O5a to
  matter at all. **Caveat (2026-11-06):** a resonance match is *retrieval overlap*, and
  wiring it straight into Suspicion would encode "the store returned a similar trace" as
  "evidence of recurrence". Define and validate the gate first — a dead input is a
  reason not to use the attribute, not a reason to wire the source early.
- **O7a — Warn at the misleading entry points, immediately.** A dated one-line note in
  `satan-attrd` `README.md` ("scaffold only") and `HANDOVER.md` ("next step: T-attr-1c"),
  and on the broker's `wiring-status.md` decay claim ("no decay implemented"). Cheap,
  verifiable, no governance decision, no behaviour change. Do it alongside the loss
  fixes; do not hold them for documentation.
- **O7b — Consolidate the governance, later.** Move the normative contract to where the
  code is (or make the cross-repo pointer bidirectional); refresh the three docs for
  real; give `satan-attrd` a doctrine backlog so its work appears in `doctrine status`
  rather than a deprecated `.spec-driver` tree; retire the `.spec-driver` residue
  honestly (archive, not silence). Depends on Q3.

### 5. Priorities I would defend

1. **F1 — stop the destruction today; preserve, do not merely suppress.** Three routes,
   only one of which is both deployable now and preserving:
   (i) **defer** — set `satan-sensor-content-enabled` nil (nil = "the probe does
   nothing", `satan-sensor-content.el:34-36`). Nothing is enqueued *and the watermark
   does not advance*, because `satan-sensor-content-probe-commit` advances only when the
   snapshot says `:emit`. The evidence therefore stays in `articles.jsonl` and lands
   whole, at full count, once the daemon accepts the reason. No schema change, no
   contract amend, no loss — only timeliness.
   **Verified 2026-11-06 against panopticon:** retention touches only `raw/` (7 days,
   and only once the same-day segment exists) and `segments/` (90 days); `content/` has
   no retention rule at all (`panopticon/segmentizer/retention.py`; its README tier table
   says "Extracted content and digests — No automatic retention yet"). `articles.jsonl`
   is append-only and shards are content-addressed, so a deferred backlog survives
   indefinitely. The cost is unbounded index growth: `read_index` and
   `satan-tools-content--read-articles-jsonl` both read the whole file on every probe,
   which is a pre-existing cost, not one the deferral creates.
   (ii) **daemon-side** — add the reason, which needs a §6S delta row and therefore a
   contract amend; this is the restoring fix and belongs in the same act as the contract
   change.
   (iii) **remap — not available.** No existing sensor reason is semantically
   equivalent: `content_backlog` is `panopticon_content_backlog` /
   `uninspected_captures`, keyed on a `captured_at` watermark (DEC-5), while
   `segment_backlog` is `panopticon_backlog` / `unprocessed_segments` with its own
   watermark and its own delta row. Remapping would encode one evidence stream as
   another, and is rejected.
   Also rejected: stop emitting while the watermark keeps advancing — that destroys the
   evidence at the broker instead of at the daemon, which is the same loss with better
   manners. **Suppression is not preservation.** The vocabulary-ownership question
   follows from whichever path is taken.
2. **O1 — durable no-silent-loss, before anything else structural.** Opaque storage of
   unknown `(source, reason)` pairs, a dead-letter carrying the error, claim expiry, and
   the broker half — advance probe watermarks on acknowledgement, not enqueue. This is
   the higher invariant; a handshake is convenience on top of it.
3. **O2 only if it is still needed after O1.** Once unknown reasons are stored opaquely
   and O3 surfaces dead-letters, a capability handshake may be redundant. Decide after
   O1, not before.
4. **O7a immediately, alongside 1–2.** Dated warnings at the three misleading entry
   points. No governance decision needed; prevents the next reader being misinformed
   while the rest of this is pending.
5. **O5b as a decision — cheap, and before any experiment.** One of measure / remove /
   keep. Removal is a single branch; measuring is a slice. Do not build the slice before
   the decision.
6. **O3 next.** Provenance plus ingestion health, sequenced after O1: without a
   dead-letter, a reader cannot tell a quiet metabolism from a lossy one.
7. **O5a as a decision, not a build.** Consumer or telemetry, before spending another
   hour on delta magnitudes or reserved sources.
8. **O7b — the consolidation**, once Q3 has an answer.
9. **O6 after O5a = consumer**, subject to the retrieval-overlap caveat above. In order:
   `resonance` (Suspicion), `tool_error` (Metamorphosis), Cruelty as a cascade (needs
   cross-attribute reads during dispatch, which the dispatcher does not do today —
   §6.3's snapshot is read-only and pre-dispatch).
10. **F5 — provisional, not a verified low risk.** Retained last, but with an early
    assessment: does the two-lineage arrangement actually collide on a deploy, and what
    does recovery cost if it does? Escalate if it blocks a deployment, conflicts, or
    threatens data. Until assessed it is an unknown, not a low risk.

### 6. Breadcrumbs

**First hour, on a host with the database and systemd** (this is the set of checks that
would settle every **[verify]** above in about ten minutes):

```bash
systemctl --user status satan-attrd
journalctl --user -u satan-attrd -n 500 | rg -i 'parse failed|unknown|schema_version|ERROR'
psql -d satan_memory -c "SELECT count(*), count(claimed_at) FROM satan_outcome_inbox"
psql -d satan_memory -c "SELECT name, value, last_decay_at FROM satan_attributes WHERE scope='global' ORDER BY name"
psql -d satan_memory -c "SELECT source, reason, count(*), max(ts) FROM satan_attribute_events GROUP BY 1,2 ORDER BY 3 DESC"
psql -d satan_memory -c "SELECT count(*) FROM satan_audit_replies"
psql -d satan_memory -c "SELECT source, reason, count(*) FROM satan_attribute_events WHERE ts > now() - interval '1 day' GROUP BY 1,2"
psql -d satan_memory -c "SELECT id, claimed_at, payload_json->>'reason' FROM satan_outcome_inbox WHERE claimed_at IS NOT NULL"
```

The third query answers "is the metabolism alive or sitting at the decay floor" (RFC-016
saw a flat 4–6 events/day of pure decay); the fourth names which sources actually fire;
the second catches F1/F2 in the act; the sixth gives the counter-delta rate that decides
whether Curiosity and Hunger saturate (§2); the seventh surfaces F3 orphans.

**If a replay harness ever lands** (O5b / measure): `satan-budget-today-total` sums token
usage across every run directory for today's date prefix under `satan-runs-dir`
(`satan-budget.el:56-66`), and `satan-budget-exceeded-p` gates spawning on it (`:68-72`).
Replay bundles written into that tree would throttle *live* ticks with replay spend —
replay artefacts need a separate root or an explicit exclusion rule.

### 7. Open questions

- **Q1 — Does the attribute layer earn a daemon?** 4.5k lines of Rust, 107 tests and a
  systemd unit currently produce eight numbers that the capsule reads (and an unwired
  tank renderer re-reads). POL-001's test ("does it use the editor as an editor?")
  justified *extracting* it; nothing yet justifies its *size*. Worth asking before
  adding a consumer, not after.
- **Q2a — Scheduling authority (O5a)?** Consumer or telemetry; and if consumer, does
  arrival gating live in the broker (a timer that reads attributes), the daemon (a
  scheduler that emits an `arrival` source), or the harness?
- **Q2b — Prompt exposure (O5b)?** Measure, remove, or keep deliberately. Independent of
  Q2a: choosing telemetry does not answer it, because the bars stay in the prompt.
- **Q3 — Where does the normative contract live** when the code and the contract are in
  different repos, and which repo's gate guards the pair? Today neither `just check`
  sees both. **A shape is now proposed** (`IMP-067` step 2, from the spec-coverage census):
  a container spec — SPEC-005, parent SPEC-002 — that owns *both* halves of the layer and
  cites the contract as its normative source, with the contract's own location settled by
  the spec rather than by habit. What remains for the operator is the form: keep
  `docs/attributes/design-contract.md` where it is and have the spec cite it, or move the
  contract's content into the spec and leave the doc as a pointer. Either way the daemon
  gets a home and the pair gets one owner.
- **Q4 — Opaque storage of unknown reasons (O1)**: does the projection need a
  zero-delta event row with `reason` as free text, or a separate quarantine table? The
  contract's §5 event schema is closed; this needs an amend either way.
- **Q5 — Is Cruelty salvageable?** With decay live, is doubt + shame ever low enough for
  headroom in practice, given Shame rises +0.30 on `harmful` and falls −0.025 on
  `worked`? If not, the attribute is decorative and should be retired rather than wired.
- **Q6 — Should the capsule show provenance (O3) or stay a bar?** The render contract is
  explicit about shape; a provenance line is a contract change and possibly a real
  behaviour change (the model may reason differently about a value it can trace).
- **Q7 — What is the outcome variable for an exposure trial?** Interventions are rare and
  the observer only classifies where one was made, so a trial can measure tool choice,
  action counts, tokens and mode — not "did SATAN help". The preregistration must fix
  this before the first arm is drawn; that, not the plumbing, is the work.

### Non-goals

Not in scope for this RFC: new attributes; per-pattern or per-hypothesis scopes (closed
by contract §3); model-writable attribute values (invariant 7); re-deriving the brief's
semantics; rescuing the epistemics roadmap through the attribute layer (that is the
pattern layer's job, and it has its own problem — see ISS-063).

existing reason has genuinely equivalent semantics. Checked here: none does (§5 item 1), so
the preserving broker route is **defer** — disable the probe so the watermark does not
advance — and the daemon-side reason remains the restoring fix. "Suppression is not
preservation."
